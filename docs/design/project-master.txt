WAYAROUND
Documento-mestre de visão, sistemas, arquitetura e desenvolvimento

0. IDENTIDADE
Nome: WayAround
Base: Minecraft NeoForge 1.21.1
Tipo: mod solo, experimental, enorme e modular
Estética: industrial punk / industrial alternativo / arqueologia tecnológica
Objetivo: criar um Minecraft no qual diferentes jogadores possam viver histórias completamente diferentes dentro do mesmo mundo.
O projeto não deve ser entendido como “um mod que adiciona muitos itens”.
A ideia central é:
Nem todo mundo vive a mesma coisa.
Um jogador pode passar horas aperfeiçoando uma roda d'água.
Outro pode construir uma ferrovia gigantesca.
Outro pode estar explorando a Antártica.
Outro pode viver isolado porque recebeu uma habilidade extremamente rara.
Outro pode gravar um documentário.
Outro pode procurar fitas antigas.
Outro pode tentar descobrir se “Seu Velho Amigo” realmente existe.
Todos estão no mesmo mundo.
Todos estão jogando o mesmo mod.
Mas nenhum deles necessariamente experimenta o mesmo jogo.

1. ESTADO ATUAL REAL DO PROJETO
Antes de qualquer futura implementação, sempre responder:
“ONDE ESTAMOS?”
Verificar:
versão exata do Minecraft;
versão do NeoForge;
nome atual do mod;
estrutura atual de pastas;
classes existentes;
sistemas já implementados;
sistemas parcialmente implementados;
bugs atuais;
dependências;
sistemas provisórios;
sistemas que já funcionam e NÃO devem ser recriados.
Regra absoluta
SE JÁ EXISTE, NÃO FAZER DE NOVO.
Antes de programar uma feature:
procurar no código;
entender o sistema existente;
reutilizar;
expandir;
somente criar um novo sistema se o anterior realmente não servir.
Não criar duas câmeras.
Não criar dois sistemas de eventos.
Não criar duas arquiteturas de veículos.
Não criar duas formas de armazenar VHS.
Não criar um novo Assembly se já houver um Assembly Engine.

2. ESTADO INICIAL ATUAL
No momento, a parte sobrenatural mais evidente já possui o:
SPECTRUM / BLUE
Esse é um dos primeiros grandes sistemas do mod.
Todo o restante deve crescer ao redor de uma arquitetura que permita chegar ao mesmo nível de complexidade sem destruir a performance.

3. FILOSOFIA GERAL
O mundo deve ter:
memória;
consequência;
envelhecimento;
construção;
destruição;
história;
exploração;
mistério;
sistemas emergentes.
A pergunta principal de toda feature deve ser:
“Isso pode interagir com o mundo?”
Uma feature é mais valiosa quando alimenta outras.
Exemplo:
Nevasca
→ acumula neve
→ aumenta peso
→ reduz visibilidade
→ desgasta estrutura
→ estrutura entra em estado crítico
→ prédio desaba
→ destroços permanecem
→ vegetação começa a crescer
→ anos depois alguém encontra uma ruína
→ encontra uma fita
→ vê o prédio funcionando antes da queda.
O objetivo é criar cadeias de consequência.

7. ASSEMBLY — O SISTEMA CENTRAL
O Assembly é uma das fundações mais importantes do WayAround.
O jogador não deve simplesmente craftar coisas importantes.
Ele deve montá-las.
A regra é:
O jogo não pergunta apenas “qual receita produz este objeto?”
Ele pergunta “como isso foi construído?”

8. ASSEMBLY PRIMITIVO
Até uma ferramenta simples pode começar com um processo.
Pedra lascada
O jogador:
pega uma pedra;
pega outra pedra;
posiciona;
golpeia;
produz uma lasca;
tenta moldar a peça.
O resultado pode variar.
Pode:
produzir uma boa lasca;
produzir uma lasca ruim;
quebrar;
ficar irregular.
Depois a pedra pode ser presa a um cabo.
A primeira ferramenta já nasce como objeto fabricado.

9. ASSEMBLY MANUAL
Montagem manual deve ser:
lenta;
trabalhosa;
barata em máquinas;
dependente de habilidade;
sujeita a erros;
fisicamente observável.
O jogador pode:
martelar;
encaixar;
girar;
prender;
apertar;
soldar;
montar;
desmontar.

10. ASSEMBLY AUTOMATIZADO
A automação é uma segunda etapa.
O jogador constrói máquinas que realizam trabalho.
Exemplos:
máquina de pregos;
torno;
prensa;
soldador;
guindaste;
esteira;
máquina de corte;
máquina de moldagem.
O jogador passa de:
“eu faço tudo”
para:
“eu construí uma fábrica que faz isso”.

11. ERRO DE FABRICAÇÃO
A automação não deve corrigir erros magicamente.
Se uma máquina:
solda torto;
posiciona errado;
aperta pouco;
instala uma peça desalinhada;
o resultado continua errado.
Uma máquina não “entende” que algo ficou ruim.
Ela apenas executa o que foi configurado para executar.

Uma máquina mal construída pode:

quebrar antes.

13. RODA D’ÁGUA

Ela pode envolver:

Se estiver danificada:

não deve automaticamente restaurá-la ao estado perfeito.

15. VEÍCULOS NÃO POSSUEM MODELOS ÚNICOS
O jogo não deve ter simplesmente:
“Zepelim Classe S Modelo X”.
Um jogador constrói o próprio zepelim.
Outro constrói outro.
O sistema analisa a máquina e classifica.
Exemplo:
Comprimento: 168 m
Motores: 10
Massa: 1.320 t
Armamento: pesado
Tripulação: 21
Estrutura: metálica

CLASSIFICAÇÃO: S

Dois veículos Classe S podem ser completamente diferentes.

16. CLASSES DE VEÍCULOS
Sistema F → S.
F
pequeno;

Intermediárias

S
A máquina deixa de parecer um simples veículo.
Ela vira uma operação.

25. NEVE ACUMULATIVA
Nevascas não apenas “trocam a textura do chão”.

Uma base pode:

ter janelas cobertas;
perder visibilidade;
ficar parcialmente soterrada.
A própria construção muda fisicamente com o tempo.

26. NOITE
A noite deve realmente ser escura.
Não tratar iluminação como decoração.
Isso deve afetar:

sobrevivência.

27. FOGO
O fogo não deve ficar limitado a um bloco.
Uma área incendiada pode:

se juntar a outra;
produzir uma massa maior;
consumir estruturas.
Materiais diferentes podem reagir de formas diferentes.

28. FUMAÇA
Incêndios grandes precisam ser visíveis a grandes distâncias.
Um jogador pode olhar para o horizonte e ver:
Uma enorme coluna de fumaça.
Sem marcador no mapa.
Sem notificação.
O mundo conta a notícia.

29. EVENTOS FÍSICOS GIGANTES
O Blue é um exemplo.
Grandes eventos devem afetar o ambiente.
Exemplo:
Blue atinge um prédio.
O prédio não deve simplesmente trocar todos os blocos por ar.
O sistema deve avaliar:
regiões estruturais;
pontos de sustentação;
partes importantes;
massa;
integridade.
Depois produzir o colapso.

30. BUILDING DEBRIS
Construções possuem estado estrutural.
Estados possíveis:
saudável;
desgastado;
comprometido;
crítico;
colapso.
Ao colapsar pode haver diferentes apresentações:
Colapso estrutural
Grande seção inclinando.
Colapso fragmentado
Pedaços e blocos caindo.
Colapso industrial
metal rangendo;
pressão;
vapor;
tubos;
explosões localizadas;
poeira;
impacto.
Os restos permanecem no mundo.

31. PERFORMANCE DE DESTRUIÇÃO
NUNCA tratar um prédio gigante como milhares de entidades físicas individuais.
Usar uma abordagem hierárquica.
O prédio pode ser agrupado em:
paredes;
vigas;
pilares;
teto;
componentes maiores.
Durante o colapso:
primeiro grandes partes;
depois debris menores.
Não transformar 30.000 blocos em 30.000 entidades físicas sem necessidade.

32. NÍVEIS DE SIMULAÇÃO
O mundo pode ter diferentes níveis de detalhe.
Próximo
Simulação completa.
Distância média
Simulação simplificada.
Muito distante
Estado resumido.
Fora do foco
Persistência histórica.
Isso é fundamental para:
incêndios;
fumaça;
animais;
máquinas;
estruturas;
veículos;
clima.
O mundo não precisa simular cada detalhe em alta fidelidade quando ninguém está perto.

60. O SPECTRUM COMO EXEMPLO DE HISTÓRIA INDIVIDUAL

Pode existir uma situação em que apenas um jogador em todo um servidor possua a habilidade.
Não é uma recompensa garantida.
Não é uma classe.
Não é um item comum.
É uma ocorrência excepcional.

61. O DONO DO SPECTRUM NÃO É UM DEUS

pode perder;
pode morrer;
pode ser surpreendido;
continua sendo um jogador.
A diferença é o potencial destrutivo.
Isso significa que uma única pessoa pode alterar completamente a história do servidor.

62. EVENTO DO BLUE
Imagine:
Um jogador começa a usar o Blue.
O mundo responde.
estruturas quebram;
pessoas correm;
máquinas são danificadas;
fumaça aparece;
prédios desabam.
Outro jogador pode estar longe, gravando tudo.
Outro está tentando evacuar.
Outro está protegendo uma máquina.
Outro nem sabe o que aconteceu.
Esse evento gera várias histórias simultaneamente.

63. INTERAÇÃO DE HABILIDADES
Habilidades sobrenaturais devem possuir física/interação.
Exemplos:
atração alterando trajetória;
fogo encontrando gelo;
eletricidade afetando água;
gravidade afetando objetos;
poderes interagindo com máquinas.
A ideia é evitar poderes isolados.

64. JUJUTSU PROCEDURAL
O sistema deve gerar uma habilidade única para cada jogador selecionado.
Não existe uma lista curta de poderes iguais para todos.
Ao despertar:
o jogo combina características.
Possíveis características:
elemento;
invocação;
regra;
movimento;
alcance;
estética;
forma;
comportamento.
A combinação cria uma identidade.

65. DOMÍNIO DE EXPANSÃO
O domínio é a representação máxima da habilidade.
Exemplo:
Habilidade:
“Zumbis”.
Domínio:
braços de zumbis;
agarrões;
terreno temático;
invocações;
mobilidade;
titãs;
regras específicas.
O domínio deve ser procedural, mas coerente com a habilidade.

66. VOICE CHAT COM INTENÇÃO
O sistema pode interpretar comandos de voz.
Exemplo:
“Blue é muito forte.”
Nada acontece.
“Blue.”
Invocação.
“Fica parado.”
Parar.
“Orbita.”
Orbitar.
O sistema deve tentar interpretar a intenção e o contexto.
Não simplesmente reagir a qualquer menção.

67. DETECÇÃO DE DUELO
Quando dois jogadores entram num confronto real:
o sistema pode observar:
dano;
frequência;
distância;
habilidades;
tempo.
Se houver evidência suficiente:
o mundo pode reconhecer o confronto.
Pode iniciar:
música;
efeitos;
apresentação;
mudanças de atmosfera.

68. “SEU VELHO AMIGO”
Categoria especial de acontecimentos não documentados.
O sistema deve manter incerteza.
Exemplo:
O jogador faz um famoso “totem de Herobrine”.
Nada acontece.
Então:
horas depois,
coisas começam a parecer estranhas.

69. FILOSOFIA DE “SEU VELHO AMIGO”
Nunca dizer claramente:
“Herobrine está aqui.”
Nunca mostrar uma interface:
“Evento Herobrine iniciado.”
Nunca confirmar completamente.
As ocorrências devem ter explicações plausíveis.
Até que várias coincidências se acumulem.

70. POSSÍVEIS ANOMALIAS
Exemplos:
portas abertas;
objetos que parecem ter mudado;
pinturas estranhas;
silhuetas distantes;
pegadas;
estruturas inexplicáveis;
gravações estranhas;
sonhos;
lugares que o jogador não lembra de ter criado.

71. SONHO DO AETHER
Uma das ideias de “bait secreto”.
O jogador dorme.
Sonha com um portal do Aether funcionando.
Pode ouvir sons.
Pode ver o portal.
Acorda.
Talvez nunca aconteça nada.
Ou talvez, posteriormente, algo aconteça.
A intenção é que o jogador pense:
“Foi só um sonho?”

72. BACKROOMS / NOCLIP
Outra anomalia não documentada.
O jogador pode, em circunstâncias muito raras, atravessar um ponto impossível.
Em vez de morrer:
cai.
Tela escura.
Surge num espaço anômalo.
Pode nunca retornar.
O mod nunca havia dito que esse lugar existia.
Isso deve ser uma descoberta da comunidade.

73. DOCUMENTAÇÃO COMO BAIT
A página pública do mod não precisa revelar tudo.
Pode apresentar apenas uma parte:
clima;
Assembly;
engenharia;
veículos;
fotografia;
VHS.
Sistemas especiais podem permanecer não documentados.
Isso cria descoberta orgânica.

74. O “ICEBERG” DO MOD
O jogador deve constantemente descobrir que havia mais coisas.
Primeiro:
“É um mod de clima.”
Depois:
“Tem Assembly.”
Depois:
“Tem indústria.”
Depois:
“Tem envelhecimento.”
Depois:
“Tem VHS.”
Depois:
“Tem poderes.”
Depois:
“Tem Lua.”
Depois:
“Tem coisas que nem estão documentadas.”

75. EXPLORAÇÃO DE PLANETAS E DIMENSÕES
O sistema de exploração pode futuramente se expandir para:
Lua;
outros planetas;
dimensões;
regiões artificiais;
mundos experimentais.
Cada local deve ser tratado como uma camada própria da experiência.

76. HISTÓRIA DO MUNDO
Depois de meses ou anos:
o servidor deve conter:
ruínas;
pontes abandonadas;
ferrovias;
destroços;
usinas desativadas;
casas cobertas por vegetação;
zepelins caídos;
navios afundados;
fotos;
fitas;
retratos;
memoriais.
A história não precisa estar em uma wiki.
Ela pode estar no mapa.

77. ARQUEOLOGIA DOS JOGADORES
Um jogador novo não precisa conhecer os fundadores.
Ele pode descobrir:
uma fita;
uma pintura;
uma locomotiva quebrada;
uma placa;
um prédio;
uma Black Box.
E reconstruir o que aconteceu.

78. PRIMEIRO OBJETIVO: CRIAR UM MUNDO BASE
Antes de implementar todas as coisas absurdas:
criar a infraestrutura que permita:
objetos persistentes;
eventos;
tempo;
materiais;
Assembly;
estado;
armazenamento.

79. SISTEMAS FUNDAMENTAIS
A arquitetura geral deve priorizar:
World State Engine
Estado persistente do mundo.
Material/Physics Engine
Características físicas e desgaste.
Assembly Engine
Montagem e máquinas.
Structural Engine
Integridade e colapso.
Environmental Engine
Clima, fogo, neve, fumaça, natureza.
Vehicle Engine
Máquinas montáveis.
Media Engine
Fotos, câmera, VHS, TV.
Event Engine
Eventos raros e acontecimentos históricos.
AI Engine
Animais, insetos e entidades.
Anomaly Engine
Eventos secretos e sobrenaturais.

80. PRINCÍPIO DE PERFORMANCE
O WayAround pode criar cenas extremamente caras.
Exemplo:
Blue
→ derruba prédio
→ centenas de partículas
→ fumaça
→ destroços
→ áudio
→ câmera gravando
→ vários jogadores assistindo.
Não assumir que o Minecraft deve simular tudo literalmente.
Usar representação inteligente.

81. DESTRUIÇÃO OTIMIZADA
Não transformar milhares de blocos em milhares de entidades.
Usar agrupamento.
Uma estrutura pode ser representada por componentes grandes.
Somente partes relevantes viram debris menores.
O restante pode ser convertido diretamente em estado persistente.

82. PARTÍCULAS OTIMIZADAS
Uma nuvem de fumaça não precisa ser centenas de entidades.
Pode ser:
uma entidade;
partículas internas;
billboard;
shader;
volumetria simplificada.
A aparência deve sugerir uma grande quantidade.
A simulação não precisa ser igualmente grande.

83. LOD E DISTÂNCIA
Objetos próximos:
simulação completa.
Objetos médios:
simulação reduzida.
Objetos muito distantes:
estado resumido.
Objetos fora do foco:
somente persistência.
Isso é essencial para o mundo gigante.

84. O QUE NÃO FAZER
Nunca começar:
“Vamos fazer tudo.”
Dividir.
Não criar:
sistema de fumaça completo;
sistema de IA de formiga;
sistema de zepelim;
sistema de VHS;
sistema de portais;
todos ao mesmo tempo.

86. PRINCIPAL REGRA DE DESENVOLVIMENTO
Toda nova feature deve responder:
ONDE ESTAMOS?
Depois:
O QUE JÁ EXISTE?
Depois:
QUAL SISTEMA EXISTENTE POSSO REUTILIZAR?
Depois:
QUAL É A MENOR IMPLEMENTAÇÃO FUNCIONAL?
Só então programar.

87. REGRA DE INTEGRAÇÃO
Toda feature importante deve tentar conversar com pelo menos um sistema existente.
Exemplo:
Fogo
deve conversar com:
materiais;

deve conversar com:

deve conversar com:

deve conversar com:

88. O MOD COMO “UMA HISTÓRIA POR JOGADOR”
O resultado desejado não é que todos os jogadores vejam todas as features.
O resultado desejado é:
Cada jogador possuir uma história diferente sobre o mesmo mundo.
Um:
“Eu passei três dias aperfeiçoando minha roda d’água.”
Outro:
“Eu passei uma semana fazendo minha ferrovia.”
Outro:
“Eu fui para a Antártica.”
Outro:
“Eu construí um zepelim.”
Outro:
“Eu encontrei uma fita de um acidente de 200 dias atrás.”
Outro:
“Eu vi o Blue destruindo uma cidade.”
Outro:
“Eu tive um sonho estranho e depois caí em um lugar que nem deveria existir.”
Todos estão corretos.
Todos estão jogando WayAround.

89. IDENTIDADE FINAL
O WayAround não deve ser:
“Minecraft com muitos mods dentro de um mod.”
Deve parecer um mundo único no qual:
engenharia;
natureza;
tempo;
história;
tecnologia;
exploração;
anomalias;
mídia;
jogadores;
existem simultaneamente.

90. FRASE CENTRAL DO PROJETO
UM ÚNICO MUNDO.
UM ÚNICO MOD.
MILHARES DE HISTÓRIAS.
NEM TODO MUNDO VIVE A MESMA COISA.

91. OBSERVAÇÃO PARA O FUTURO GPT
Quando esta descrição for usada em uma nova sessão, NÃO presumir que qualquer uma dessas features já esteja implementada.
Apenas o que estiver presente no código/estado atual deve ser considerado existente.
Antes de alterar qualquer coisa:
ONDE ESTAMOS?
Descobrir.
Depois:
O QUE JÁ EXISTE?
Depois:
O QUE ESTÁ FALTANDO?
Depois:
QUAL É O PRÓXIMO BLOCO MAIS FUNDAMENTAL?
Nunca reimplementar uma coisa existente apenas porque a ideia apareceu novamente.
Nunca transformar o documento inteiro em uma tarefa única.
O projeto é modular.
Cada sistema deve poder nascer, funcionar sozinho e posteriormente conversar com os outros.
O objetivo não é terminar tudo de uma vez.
O objetivo é construir uma fundação suficientemente boa para que, ao adicionar a próxima ideia absurda, ela possa realmente fazer parte do mesmo mundo.
